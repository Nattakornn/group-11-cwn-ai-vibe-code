# สรุป requirement แบบ conceptual 1 หน้า (concept-one-pager)

ผลลัพธ์หลัก: `work/<YYYY-MM-DD>-<ชื่อลูกค้าสั้น>-concept-1page.docx` ไฟล์เดียว ภาษาไทย **ไม่เกิน 1 หน้า A4**
ผลลัพธ์เสริม (เมื่อผู้ใช้ขอภาพผู้บริหาร): `work/<YYYY-MM-DD>-<ชื่อลูกค้าสั้น>-exec-summary.png` ดูขั้นที่ 8
ผู้อ่านมี 2 กลุ่มพร้อมกัน: **ลูกค้า** (อ่านเพื่อยืนยันว่าเราเข้าใจถูก) และ **ทีม SA/Presales** (อ่านเพื่อทำ spec ต่อ)
→ ภาษาต้องสุภาพ อ่านง่ายสำหรับคนที่ไม่ใช่สายเทคนิค และชัดพอให้ SA เอาไปทำต่อได้

## Input ที่รับ

- โน้ตที่เซลส์จดเอง มักเป็น bullet สั้น ๆ ไม่เรียงลำดับ อาจมีตัวย่อหรือคำติดปาก
- Transcript หรือไฟล์ถอดเสียงประชุม (Teams/Zoom)
- โน้ตแบบตาราง Excel (.xlsx) ที่มักแบ่งหัวข้อ ปัญหา / As is / To be ต่อระบบ
  - As is → Before และ To be → After ได้ตรง ๆ
  - อ่านทุกชีต และแปลงวันที่ที่เป็นตัวเลข serial ของ Excel เป็นวันที่จริง (เช่น 46325 = 30 ต.ค. 2026)
  - ถ้าไม่มี `openpyxl` ให้แตกไฟล์ .xlsx เป็น zip แล้วอ่าน `xl/sharedStrings.xml` กับ `xl/worksheets/*.xml` ด้วย Python ที่มีมากับเครื่อง
- ถ้ามีทั้งโน้ตและ transcript ให้ถือ transcript เป็นหลักฐานหลัก และใช้โน้ตบอกว่าเซลส์ให้น้ำหนักเรื่องไหน
- ไม่มี input เลย → ถามผู้ใช้ **ห้ามแต่ง requirement เอง**

### ตรวจว่าภาษาไทยไม่เสียก่อนเริ่ม

ไฟล์ .txt ที่ export หรือ copy มาจาก Excel มักเสียภาษาไทยกลายเป็น `???` ทั้งไฟล์ เพราะบันทึกเป็น ANSI แทน UTF-8
- เจอ `?` ติดกันหลายตัวแทนข้อความไทย → **หยุด** อย่าเดาเนื้อหาจากคำอังกฤษหรือตัวเลขที่เหลืออยู่
- หาไฟล์ต้นฉบับชื่อใกล้เคียงกันในโฟลเดอร์เดียวกันหรือใน Downloads (มักเป็น `.xlsx`) ถ้าเจอให้อ่านจากไฟล์นั้น
- ถ้าไม่เจอ ให้บอกผู้ใช้ส่งไฟล์มาใหม่ เป็น `.xlsx` หรือบันทึกเป็น CSV UTF-8 หรือบอก path ของไฟล์ต้นฉบับ

## ขั้นตอน

1. **อ่าน input ทั้งหมด** แล้วแยกเป็น 3 กอง:
   - ✅ **ลูกค้าพูดชัด**: มีในโน้ตหรือ transcript ตรง ๆ
   - ❓ **ไม่ชัดหรือขาด**: ลูกค้าพูดกว้าง ๆ ขัดกันเอง หรือไม่ได้พูดถึงเลย
   - 🚫 **ห้ามลงเอกสาร**: ราคา งบ กำหนดส่งมอบ ค่า MA ชื่อ tech stack ความเห็นหรือการประเมินของเซลส์ ข้อมูลภายในบริษัท ชื่อผู้เข้าประชุม (ดูหัวข้อ "กติกาที่ห้ามข้าม")
   - กรณีก้ำกึ่ง เช่น ช่องทางที่ลูกค้าระบุเอง หรือตัวเลขที่ขัดกัน ให้ตัดสินตาม "แนวตัดสินกรณีก้ำกึ่ง" ใน `references/one-pager-template.md`
2. **เขียนเนื้อหา 3 หัวข้อหลัก** ตาม `references/one-pager-template.md`
   1. **ปัญหาและเป้าหมายธุรกิจ (Why)**: ตอนนี้ลูกค้าเจออะไร และอยากได้ผลอะไรในมุมธุรกิจ เขียนด้วยคำของลูกค้า
   2. **ผู้ใช้และฟีเจอร์หลัก (Scope)**: ใครใช้ระบบบ้าง และแต่ละกลุ่มทำอะไรได้ ใส่สิ่งที่อยู่นอกขอบเขตถ้าลูกค้าพูดถึง
   3. **ภาพ concept แบบ Before / After**: ตารางสองคอลัมน์ เทียบวิธีทำงานตอนนี้กับหลังมีระบบ 3–5 แถว ตามขั้นตอนงานจริงของลูกค้า
3. **จัดการข้อมูลที่ไม่ชัด (กอง ❓)**: เขียนลงในหัวข้อที่เกี่ยวข้องเป็น **สมมติฐาน** และทำเครื่องหมาย `[สมมติฐาน]` เป็นตัวเอียงสีเทา เพื่อให้ลูกค้ายืนยันหรือแก้ได้ตรงจุด
   - เขียนเป็นประโยคที่ลูกค้าตอบได้ทันที เช่น "*[สมมติฐาน] ผู้ใช้หลักคือพนักงานสาขา ประมาณ 50 คน*"
   - ห้ามเขียนสมมติฐานให้ดูเหมือนข้อเท็จจริง
4. **ตัดให้จบใน 1 หน้า**: ถ้ายาวเกิน ให้ลดขนาดฟอนต์ก่อน (ไม่ต่ำกว่าที่กำหนดในขั้นที่ 5) ถ้ายังเกินจึงตัดเนื้อหาตามลำดับนี้
   - รายละเอียดฟีเจอร์ย่อย
   - แถว Before/After ที่ซ้ำความหมายกัน
   - คำอธิบายเกริ่น
   - **ห้ามตัดสมมติฐานที่ต้องให้ลูกค้ายืนยัน**
5. **สร้างไฟล์ .docx**
   - เขียนสคริปต์ด้วย npm `docx` (โหลด skill `docx` ก่อนถ้ามี เพื่อดูข้อควรระวัง)
   - ถ้า `require('docx')` ไม่เจอ ให้ติดตั้งในโฟลเดอร์ scratchpad (`npm install docx@9.5.1`) แล้วรันสคริปต์จากที่นั่น **ห้ามติดตั้งลงโต๊ะทำงานหรือโปรเจกต์**
   - เก็บสคริปต์ไว้ใน scratchpad ส่วนใน `work/` ให้มีแต่ไฟล์ผลลัพธ์
   - กระดาษ A4 ขอบ 2 ซม. ฟอนต์ Leelawadee UI (มีในทุกเครื่อง Windows)
   - ขนาดตัวอักษร: เนื้อหา 9.5–11 pt และตาราง 8.5–10 pt เริ่มจากตัวใหญ่ก่อน แล้วค่อยลดถ้าไม่จบใน 1 หน้า
   - ถ้าลูกค้ามีหลายระบบ (4 ระบบขึ้นไป) มักต้องใช้ 9.5 / 8.5 pt
   - หัวกระดาษ: ชื่อลูกค้า · "สรุปความเข้าใจเบื้องต้น (Conceptual Requirement)" · วันที่ประชุม · "ฉบับร่างเพื่อยืนยัน"
   - Before/After ทำเป็นตาราง 2 คอลัมน์ หัวตารางมีสีพื้นอ่อน มีลูกศร → คั่นกลางหรือใส่ในหัวตาราง
   - ท้ายหน้าใส่ 1 บรรทัด: "หากข้อใดไม่ตรงกับความต้องการ กรุณาแจ้งกลับเพื่อปรับแก้ก่อนจัดทำรายละเอียดขั้นถัดไป"
6. **ตรวจก่อนส่ง** ตามเช็กลิสต์ใน `references/one-pager-template.md`
   - ต้องได้ 1 หน้าจริง **ต้องนับหน้าทุกครั้ง ห้ามกะเอา**
     - เครื่องที่มี Microsoft Word: เปิดไฟล์ผ่าน PowerShell COM (`Word.Application`) อ่าน `ComputeStatistics(2)` ต้องได้ 1 แล้ว `ExportAsFixedFormat(<pdf>, 17)` เป็น PDF เก็บใน scratchpad
     - เครื่องที่มี LibreOffice: `soffice --headless --convert-to pdf` แล้วนับหน้า
   - เปิด PDF ดูด้วยตา: ตารางไม่ล้นขอบ ภาษาไทยไม่เพี้ยน และไม่มีบรรทัดเดียวตกไปหน้า 2
   - ไม่มีตัวเลขเงิน วันส่งมอบ หรือชื่อเทคโนโลยี
   - ไม่มีเบอร์โทรหรืออีเมลส่วนตัวของลูกค้า
7. **สรุปให้ผู้ใช้ในแชต (ไม่อยู่ในไฟล์)**
   - path ของไฟล์
   - จำนวนสมมติฐานที่ต้องให้ลูกค้ายืนยัน
   - ระบุว่าอ่านจากไฟล์ไหน โดยเฉพาะเมื่อไฟล์ที่ผู้ใช้ส่งมาเสีย แล้วต้องไปใช้ไฟล์ต้นฉบับแทน
   - เรื่องที่ตัดออกเพราะห้ามลงเอกสาร ทำเป็นตาราง "ข้อมูล → ส่งต่อใคร"
     - ราคา · ค่า MA → `fin-joy` (`pricing-calc`)
     - รูปแบบติดตั้ง · tech stack · spec → `sa-ton` (`req-to-spec`)
     - timeline → ทีมขายใช้ภายใน
     - งานที่เซลส์ต้องไปทำต่อ เช่น "คุยกับแผนก IT" → next step ของผู้ใช้
     - ชื่อบุคคล → ไม่ใส่ตามนโยบายข้อมูลลูกค้า
   - สิ่งที่ดูผิดปกติในโน้ต เช่น วันที่ใน timeline อยู่ก่อนวันประชุม หรือตัวเลขขัดกันเอง ให้เตือนผู้ใช้ตรวจก่อนวางแผนต่อ
   - เรื่องก้ำกึ่งที่ตัดสินเอง (ใส่หรือไม่ใส่) พร้อมเหตุผลสั้น ๆ ให้ผู้ใช้ตรวจ
8. **ภาพสรุปผู้บริหาร (PNG) ทำเฉพาะเมื่อผู้ใช้ขอ** เช่น "ทำภาพสรุปผู้บริหารให้หน่อย"
   - ใช้เนื้อหาจาก .docx ที่ผ่านขั้นที่ 1–6 แล้วเท่านั้น ห้ามเพิ่มข้อมูลใหม่ กติกาห้ามข้ามทุกข้อยังใช้เหมือนเดิม
   - ผู้อ่านคือผู้บริหาร: อ่านจบใน 30 วินาที ตัดรายละเอียดเหลือเฉพาะเป้าหมาย ตัวเลขขนาดปัญหา และวันนี้ → หลังมีระบบ
   - คัดลอก `references/exec-summary-template.html` ไปไว้ใน scratchpad แล้วแทนเนื้อหาตามคอมเมนต์ที่หัวไฟล์
     - **สไตล์ห้ามเปลี่ยน**: คลีน เว้นที่ว่างเยอะ ไม่มีกรอบหรือกล่องสี ใช้โทนน้ำเงินชุดเดียวทั้งภาพ (ครึ่งบนน้ำเงินเข้ม ครึ่งล่างฟ้าอ่อนมาก)
     - ตัวเลขที่เป็นสมมติฐานใส่ `*` และอธิบายใน footer · ห้ามใช้ราคา งบ หรือค่า MA เป็นตัวเลขเด่น
     - 1 คอลัมน์ = 1 ระบบหรืองาน ใช้ 3–5 คอลัมน์ ถ้ามีมากกว่า 5 ให้รวมงานที่คล้ายกัน
   - เรนเดอร์ด้วย Edge หรือ Chrome แบบ headless ขนาด 1600×900 scale 2 (ได้ 3200×1800)
     ```powershell
     & "C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe" --headless=new --disable-gpu --hide-scrollbars `
       --force-device-scale-factor=2 --window-size=1600,900 "--user-data-dir=<scratchpad>\edge-prof" `
       "--screenshot=<work>\<YYYY-MM-DD>-<ลูกค้า>-exec-summary.png" "file:///<scratchpad>/exec.html"
     ```
   - **เปิดดูภาพทุกครั้ง** แล้วแก้ใน HTML จนผ่าน:
     - ไม่มีข้อความชนเส้นหรือล้นขอบ
     - ไม่มีพื้นที่ว่างก้อนใหญ่ท้ายภาพ
     - คำภาษาไทยไม่ถูกตัดกลางคำจนอ่านผิด (แม่แบบตั้ง `word-break: keep-all` ไว้แล้ว ถ้ายังตัดผิด ให้ปรับถ้อยคำหรือใส่ `&nbsp;`)
   - ในแชตให้บอกว่าตัดอะไรออกจาก .docx เพื่อให้ภาพสั้นลง และย้ำว่าภาพแก้หรือคอมเมนต์ไม่ได้ ถ้าต้องการให้ลูกค้ายืนยันความเข้าใจ ให้ส่ง .docx

## กติกาที่ห้ามข้าม

- **ห้ามเกิน 1 หน้า A4**
- **ห้ามใส่ราคา งบประมาณ ค่า MA หรือกำหนดส่งมอบ** แม้ลูกค้าจะพูดถึงก็ตาม เพราะยังไม่ผ่านการประเมิน ให้แจ้งผู้ใช้ในแชตแทน
- **ห้ามระบุ tech stack** (ชื่อภาษา framework cloud vendor หรือรูปแบบติดตั้ง เช่น On Premise) เอกสารนี้เป็น conceptual ต้องไม่ผูกมัดทีม SA
  - ข้อยกเว้น: ช่องทางหรือความสามารถที่ลูกค้าระบุเองว่าต้องการ เช่น "ดูสลิปผ่าน TTB Touch" หรือ "ให้ AI กรอง" ใส่ได้ เพราะเป็นความต้องการของลูกค้า
- **ห้ามใส่ข้อมูลภายในหรือความเห็นของเซลส์** เช่น "ลูกค้างบน้อย" "คู่แข่งเสนอถูกกว่า" "ดีลนี้น่าจะปิดได้"
- **ห้ามแต่ง requirement**: ถ้าไม่มีใน input ต้องเขียนเป็น `[สมมติฐาน]` หรือไม่เขียนเลย
- ปฏิบัติตามนโยบายข้อมูลลูกค้า (`customer-data-policy`): ไม่ใส่ชื่อ เบอร์ หรืออีเมลของบุคคล รวมถึงชื่อผู้เข้าประชุมทั้งฝั่งลูกค้าและฝั่งเรา ให้ใช้ชื่อองค์กรและตำแหน่งแทน
